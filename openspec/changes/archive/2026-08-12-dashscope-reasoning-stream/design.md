## Context

The chat pipeline currently flows: `useChat` (client) → `/api/chat` → `streamText()` (server,
from `ai` package) → `@ai-sdk/openai` provider → `/api/llm` gateway → Bailian DashScope.

`@ai-sdk/openai@0.0.66` does not parse `reasoning_content` from the upstream SSE, so reasoning
tokens are discarded at the SDK adapter layer. The gateway (`api.llm.$.ts`) already passes the
SSE through unchanged — the field is present, just not consumed.

`ai@4.0.18` is installed (with `@ai-sdk/ui-utils@1.0.5`). The AI SDK data-stream wire
format is line-based: `<code>:<JSON>\n`, one part per line. Verified part codes: `0:` text
(string → appended to `message.content`), `2:` data (array), `3:` error, `8:` message_annotations
(**array** → pushed into `message.annotations`), `9/a/b/c:` tool parts, `d:` finish_message,
`e:` finish_step. **There is no reasoning-delta part in this SDK version** —
`toDataStreamInternal` only handles text-delta, tool parts, error, step-finish, and finish.
The client `useChat` (`processChatResponse`) parses these lines: `0:` appends to
`message.content`, `8:` arrays accumulate into `message.annotations`, `d:` feeds the
`onFinish` usage, and `e:` controls message splitting via `createNewMessage = !isContinued`.
Importantly, EVERY parsed part (including each `8:` annotation) triggers a full React state
update with a deep-copy of the message, so annotation emission MUST be throttled.

The `SwitchableStream` in `api.chat.ts` allows switching the active source mid-flight, which
is used for continuation segments and the trailing usage annotation.

## Goals / Non-Goals

**Goals:**
- Bypass `@ai-sdk/openai` for the platform default model; call the gateway directly with `fetch`
  and parse SSE manually to extract both `reasoning_content` and `content`.
- Produce AI SDK data-stream wire format (`0:` for text, `8:` for annotations) so `useChat`
  works unchanged.
- Stream reasoning as incremental `8:` annotations of type `reasoning` so they land in
  `message.annotations`.
- Keep `SwitchableStream` continuation segment logic working.
- Keep the existing usage annotation, telemetry, and persistence pipelines untouched.

**Non-Goals:**
- Not replacing `useChat` or the AI SDK data-stream protocol on the client.
- Not installing `dashscope-sdk-official` — raw `fetch` is sufficient and avoids a new
  dependency. The user's original request was "use Alibaba's SDK, not OpenAI" — the gateway
  already speaks Bailian's protocol; the point is to stop using `@ai-sdk/openai` as the
  SSE consumer.
- Not adding `enable_thinking` toggle (future work).
- Not changing BYOK paths — those still use `@ai-sdk/openai` via `getOpenAILikeModel`.

## Decisions

### D1: Custom streaming function replaces `_streamText` for the platform model

**Decision**: Create a new `dashScopeStreamText()` function in `stream-text.ts` that replaces
the `ai` package's `_streamText()` for the platform default model. It calls `/api/llm` via
`fetch`, parses SSE manually, and returns an object compatible with the existing `SwitchableStream`
pipeline.

**Rationale**: `_streamText` from `ai` delegates SSE parsing to `@ai-sdk/openai`, which is the
exact layer that discards `reasoning_content`. Replacing just the provider adapter
(`getOpenAILikeModel`) is impossible because `@ai-sdk/openai@0.0.66` has no hook for custom
delta parsing. Replacing the entire `streamText` call is the cleanest cut.

**Alternatives considered**:
1. Upgrade `@ai-sdk/openai` to 1.x — risks breaking changes across the bolt.diy fork's
   provider abstraction; untested with `ai@4.0.18`.
2. SSE TransformStream at the gateway — hacky (rewrites `reasoning_content` into `content`
   with marker tags), pollutes the message parser, and doesn't give clean reasoning/answer
   separation.
3. `dashscope-sdk-official` — adds a dependency for what is essentially a `fetch` + SSE parse
   that's ~80 lines of code. The SDK's chat-completions streaming returns the same OpenAI-
   compatible chunks, so there's no advantage over raw `fetch`.

### D2: Return a `ReadableStream<Uint8Array>` in data-stream wire format

**Decision**: `dashScopeStreamText()` returns a `ReadableStream<Uint8Array>` that directly
produces AI SDK data-stream lines (`0:"text"\n`, `8:[...]\n`, `e:{...}\n`). `api.chat.ts`
feeds this into `SwitchableStream.switchSource()` just like the current
`result.toDataStream()` output.

**Rationale**: The AI SDK's `createDataStream` + `DataStreamWriter` has no `writeTextDelta`
method — text deltas (`0:` parts) are normally generated by the model adapter, not by user
code. Manually constructing the wire format is simpler than reverse-engineering the
`DataStreamWriter` internals, and the format is stable (it's the documented data-stream
protocol that `useChat` parses).

**Wire format produced** (verified against `@ai-sdk/ui-utils@1.0.5` sources):
```
8:[{"type":"reasoning","value":{"text":"reasoning delta"}}]\n   ← thinking phase, throttled ~200ms
0:"answer text delta"\n                                          ← answer phase, one line per delta
e:{"finishReason":"stop","isContinued":false}\n                  ← end of every segment; see D8
8:[{"type":"usage","value":{...}}]\n   ← appended by the existing createDataStream pipeline
```

**Alternatives considered**:
1. Use `createDataStream` and write reasoning via `writeMessageAnnotation`, text via
   `writeData` — but `writeData` emits type `2` (custom data), not type `0` (text-delta);
   `useChat` won't accumulate it into `message.content`.
2. Write everything as annotations — but `message.content` would stay empty during streaming,
   breaking the message parser, file actions, and preview.

### D3: Reasoning as incremental message annotations (`type: 'reasoning'`)

**Decision**: Reasoning deltas are emitted as `8:` parts (code for `message_annotations`), each
carrying a single-element array: `8:[{"type":"reasoning","value":{"text":"<delta>"}}]\n`.
This matches exactly what `writeMessageAnnotation` produces (verified in `ai@4.0.18` source).
The client concatenates all `text` fields from `reasoning`-type annotations to display the full
reasoning.

**Rationale**: `message.annotations` is the AI SDK's extensible side-channel — it's already
used for `usage` and `telemetry` annotations. Reasoning fits naturally as another annotation
type. `useChat` accumulates annotations without changes. `processChatResponse.onMessageAnnotationsPart`
pushes each array into the accumulator and assigns it to `message.annotations`.

**Trade-off**: Each `8:` part triggers a full `execUpdate()` including a deep JSON round-trip
copy of the message (`processChatResponse.execUpdate`). Emission MUST be throttled (~200ms)
to keep re-render cost bounded during a 70s thinking phase. The client filters and joins
annotations by `type` — the same pattern already used for `usage` in `AssistantMessage.tsx`.

**Alternative considered**: Emit reasoning as a reasoning-delta part — impossible: `ai@4.0.18`
has no such part type (verified in `dataStreamParts`; unknown codes throw on the client).

### D4: `onFinish` callback contract preserved

**Decision**: `dashScopeStreamText()` accepts the same `onFinish` callback as the current
`streamText()`, invoked when the upstream stream ends with `{ text, finishReason, usage }`.
This keeps `api.chat.ts`'s continuation segment logic (`finishReason === 'length'`) unchanged.

**Rationale**: The continuation logic in `api.chat.ts` (L83-L173) is triggered by `onFinish`.
By matching the callback contract, we avoid touching that code path.

### D5: `firstReasoningTokenAt` tracked alongside `firstVisibleTokenAt`

**Decision**: Add a `firstReasoningTokenAt` timestamp in `api.chat.ts`, set when the first
`reasoning_content` delta is parsed. Include it in the timing annotation alongside the existing
`firstVisibleTokenAt`.

**Rationale**: WB-09 already defines TTFT as "first content token, not reasoning." Adding TTRT
gives observability into the thinking phase duration without changing the TTFT definition.

### D6: Client "thinking" state in the state machine

**Decision**: Add a `thinking` state between `waiting` and `streaming` in `Chat.client.tsx`'s
`requestStatus` state machine. Transition `waiting → thinking` when the first `reasoning`-type
annotation arrives; transition `thinking → streaming` when `message.content` starts growing.

**Rationale**: The existing `useEffect` (L267-L281) watches `message.content` length to detect
streaming start. Reasoning annotations arrive before content, so we need an earlier transition
point. `ResponseStats.tsx` shows "思考中… X.Xs" during `thinking`, then switches to
"生成中… X.Xs · N tok/s" during `streaming`.

### D7: Collapsible reasoning panel in `AssistantMessage.tsx`

**Decision**: Render a `<details>` (or equivalent) panel above the `<Markdown>` content,
populated from `message.annotations.filter(a => a.type === 'reasoning')`. Auto-expand during
live streaming, collapsed-by-default on reload.

**Rationale**: `<details><summary>` is the simplest collapsible that works without extra
dependencies. During live streaming, the panel auto-expands (controlled by `requestStatus ===
'thinking'`). On reload, it defaults to collapsed (the `open` attribute is not set for
historical messages).

### D8: Emit `e:` finish_step per segment; omit `d:` finish_message

**Decision**: Each `dashScopeStreamText()` segment ends with an `e:` part
(`{"finishReason":<reason>,"isContinued":false}`), matching what today's
`result.toDataStream()` emits. No `d:` part is emitted.

**Rationale** (verified against `ai@4.0.18` and `processChatResponse` sources):
- `maxSteps` defaults to 1 and `experimental_continueSteps` to false, so the current pipeline
  ALWAYS emits `isContinued: false`. The client sets `createNewMessage = !isContinued`, so
  today every continuation segment starts a NEW assistant message in the UI. Emitting `e:`
  with `isContinued: false` reproduces this exactly.
- Omitting `e:` entirely would leave `createNewMessage` false, causing all segments to
  accumulate into one message — an observable behavior change. Rejected.
- `d:` only feeds `response.usage` into `useChat`'s `onFinish`; `Chat.client.tsx` merely
  `console.log`s it. Real usage/timing reach the client via the trailing `usage` annotation
  (`8:`), which is untouched. Omitting `d:` is invisible.
- The trailing `usage` annotation arrives after the last `e:`; since `e:` never resets the
  annotations accumulator (only message creation), it attaches to the last segment's message
  — same as today.

## Risks / Trade-offs

- **[SSE parsing correctness]**: Partial `data:` lines split across network chunks could
  cause JSON parse errors or lost deltas.
  → **Mitigation**: Buffer incomplete lines in a `TextDecoder` + string buffer; only parse
  complete lines ending with `\n`. Flush the buffer on stream end.

- **[Annotation volume]**: A 70s thinking phase producing reasoning at ~50 tok/s generates
  ~3,500 reasoning annotation objects on the message. This may bloat persisted message JSON.
  → **Mitigation**: Throttle reasoning annotation emission to one per ~200ms (not one per
  delta). The client renders the accumulated text; throttling only reduces annotation count,
  not content completeness. Persisted message size stays manageable.

- **[Wire format stability]**: Manually producing `0:`, `8:`, and `e:` lines couples to the
  AI SDK data-stream protocol, which could change in future SDK upgrades.
  → **Mitigation**: The protocol is stable in `ai@4.x` and `useChat` is the only consumer.
  If the SDK is upgraded later, the wire format producer can be replaced with `createDataStream`
  if newer versions add `writeTextDelta`.

- **[BYOK regression]**: The `OpenAILikeProvider` still uses `getOpenAILikeModel` for BYOK
  paths. The new `dashScopeStreamText` only applies to the platform default model.
  → **Mitigation**: `stream-text.ts` branches: if the resolved provider/model is the platform
  default and BYOK is disabled, use `dashScopeStreamText`; otherwise, fall back to the existing
  `_streamText` path. No BYOK code changes.

- **[`dashscope-sdk-official` not used]**: The user asked about using Alibaba's SDK. We're
  using raw `fetch` to the gateway instead, which calls Bailian's OpenAI-compatible endpoint.
  The gateway already handles credential injection and auth.
  → **Mitigation**: The gateway IS Alibaba's protocol. The point of the change is to stop
  `@ai-sdk/openai` from discarding `reasoning_content`. Raw `fetch` + SSE parsing achieves
  this without a new dependency.
